## Design invariants
- **Run test suites only at the end of a task, never while iterating.** The full engine suite takes about 5 minutes of run time plus a 35 s - 1 min build (`audit_invariants` alone 70 s, `open_items_d` 46 s, `stage0` / `seventh_pass` / `audit_fixes` ~23 s each), by design: those are randomised invariant sweeps and long simulations, and they are kept long on purpose, not trimmed for speed. While working use `cargo check` / `tsc` / `npm run build`, and at most one targeted binary (`cargo rtest --test <name>`) when a specific gate is needed. Run the whole suite (`cargo rtest`, node suites, `pytest tests`) once, when the work is finished. Never launch the suites in the foreground repeatedly or "to see if it still works".
- **Intrinsic data in, models for the environment.** The simulation relies as much as possible on *intrinsic* values for each
  compound (properties that do not depend on conditions): standard enthalpy and entropy of formation, heat-capacity
  parametrisation, molar mass, molecular structure, acid dissociation constants at a reference state, standard
  potentials, solvation / activity parameters. Quantities that depend on external factors (melting and boiling point,
  vapour pressure, solubility, density at a temperature, pH, state of matter) are *derived* with equations and models
  (Gibbs energy and K(T), Clausius-Clapeyron / Clapeyron, Raoult / Henry / activity models, Antoine, van't Hoff, ...) from
  the vessel's temperature, pressure, composition and solvent. Never store a condition-dependent value as if it were a
  property of the compound; if a database only offers one (e.g. a normal boiling point), store it as a labelled *point on
  a curve* (e.g. (T, 101325 Pa) for the vapour-pressure fit) and derive everything else from it. Phase is never stamped at
  import. When a derived value must be estimated, label its provenance tier (Tabulated / Imported / Estimated /
  Speculative) and prefer sources in order: measured intrinsic data -> group-additivity / semi-empirical estimates.
- Products are compounds exactly like reagents (same import path, same data), because a product can be the next reactant.
- **Master plan for generalisation: `docs/plans/generalization-master-plan.md`** (audit of how every reaction outcome is determined, model choices, the minimal large-database stack, staged implementation with numeric gates). Evidence and probe scripts: `docs/plans/generalization-audit/`. Older background: `COMPOUND_PHASE_PLAN.md`, `docs/plans/generality-audit.md` (F1–F47), `docs/plans/data-sources.md`.

## Quickstart
```bash
# Full local version: rebuilds the WASM engine and the web app when their sources changed, starts the server, opens the
# browser. No rate is computed during or after a session: reaction rates come from measured data (`engine/data/rates_measured.json`).
python3 run.py

# Run tests
pytest tests/ -v

# Run engine tests (run them only at the end of a task; `cargo test` now uses the same optimised profile as `cargo rtest`; fast: `release-test` profile = release optimisation without fat LTO, cold build ~1 min instead of ~5;
# `cargo test --release` is the same tests under the shipped LTO profile)
cd engine && cargo rtest

# Build WASM engine (run.py does this when stale)
cd engine && cargo build --release --target wasm32-unknown-unknown && wasm-bindgen target/wasm32-unknown-unknown/release/reaction_chamber_engine.wasm --out-dir ../web/src/wasm/engine --target web

# Build bundle
python3 pipeline/build_bundle.py

# Build frontend (run.py does this when stale)
cd web && npm run build
```

## External dependencies (for the eventual README)

The repository will become user facing: someone who clones it and runs `python3 run.py` must get the same app. What an
installer can do and what it cannot:

| Dependency | Needed for | Automatable | How |
|---|---|---|---|
| Python >= 3.10 + `requirements-dev.txt` | local server, tests | yes | `pip install -r requirements-dev.txt` (`requirements.txt` is the small runtime set of the hosted API, see Deployment) |
| Node.js >= 20 + npm | web build | Node: no (system installer); packages: yes (`run.py` runs `npm install` when `web/node_modules` is missing) | https://nodejs.org |
| Rust (stable) + `wasm32-unknown-unknown` target + `wasm-bindgen-cli` **0.2.100** (must equal the `wasm-bindgen` version in `engine/Cargo.lock`) | WASM engine build | yes, once rustup exists | `rustup target add wasm32-unknown-unknown`; `cargo install wasm-bindgen-cli --version 0.2.100` |

Hardware target: 8 GB RAM.

Licences of shipped data are flagged in `docs/plans/local-full-engine-plan.md` (user decision 2026-10-06: integrate
first, resolve before the site is announced).

- **Test speed and the species-store deadlock (2026-10-04)**: the multi-minute "slow" test runs were partly a hang, not computation. The species store sat behind a `std::sync::RwLock`, which stops *new* readers while a writer waits; the engine reads the store from inside its own call chains (e.g. `henry_species` held a read guard while `try_thermo_state` took another), so a parallel test registering a species left a writer waiting on the first guard and the nested read waiting on the writer: every thread asleep, load 0 (found with `gdb -p <pid> -batch -ex "thread apply all bt"`). `engine/src/db/lock.rs` (`StoreLock`) admits readers whenever no writer is *active* (nested reads never block) and panics, instead of hanging, when a thread requests the write lock while holding a guard of the same lock; never hold a store guard across a call that may register a species. Compile time was the other cost: `lto = true` re-links the engine with fat LTO for each of the 30 test binaries (cold `cargo test --release --no-run` 4 min 45 s); the `release-test` profile (`Cargo.toml`, alias `cargo rtest` in `engine/.cargo/config.toml`) has the same opt-level and gives the same results and run times with a 1 min build (full suite 1 min 4 s run). The 50-species benchmark gate times five batches and takes the best, so CPU contention from parallel tests cannot fail it.
